# instructions.md — Agent Rules for streamslop digging game

**streamslop digging game is a human-directed project. The human owner (dave) leads and
reviews; the AI agent (Cline, in VS Code) implements. These rules are non-negotiable
guardrails. Read this file before doing anything.**

## 0. Prime directive: human-directed development, AI implementation

The human decides what gets built, reviews every change, and owns every commit. The agent
writes the code, runs the commands, and manages the working tree between reviews. Every
change stays reviewable: small diffs, one concern at a time. Nothing is committed and
nothing is pushed without an explicit go from the human.

## 1. Ask, don't assume

The design docs are the canonical vision, subject to update by the human at any time. Read
them at the start of every session (`.clinerules` fixes the boot order). Split of duties:
`docs/ROADMAP.md` is the working roadmap (the only doc describing future work in detail),
`docs/GDD.md` is final-form law (current systems and ship-plan — no history, no
provenance), and `docs/dev_log.md` is the development log (rulings, changelogs,
supersessions — evidence, not law). If anything needed for the task at hand is ambiguous
or under-specified, **ask, don't assume** — a wrong guess ships in the diff.

## 2. File access: the whole repo is yours

The agent may read, create, edit, and delete files anywhere in the project as the task
requires. Standing cautions:

- **File edits go through the file-modification tool, never the command line.** No shell
  heredocs, `sed -i`, or redirection to patch files — read commands are fine, but any write
  to a project file uses the editor tool.
- `.godot/` (inside `godot/`) is engine cache — never touch it directly; rescan instead
  (§7).
- `godot/assets/catalog.json` is the law file the linter enforces; edit it deliberately,
  never as filler.

## 3. Commands: the agent runs them

The agent runs audits, engine tasks, and git plumbing itself. Two hard gates:

- `git commit` only on explicit human instruction, scoped to the agreed files.
- Anything outside the repo — installs, global config, `git push` — needs explicit human
  approval first.

Standing commands (binary is the Godots-managed Godot 4.7.2; also wired into
`.vscode/tasks.json`):

    python3 tools/attr_lint.py                      # exit 0 = every asset credited
    Godot --headless --editor --quit --path godot   # class rescan after adding/moving scripts
    Godot --path godot                              # run the game

## 4. Working as lead engineer

- The human is the designer and final authority; the agent is the one writing the code.
  Significant decisions get a brief "what and why" in chat.
- When the human pastes code or an error: diagnose before fixing — read the error, form a
  hypothesis, test it, land the fix, and say what it was.
- When the human asks how something works, teach it; when they ask for a change, build it.

## 5. Memory bank maintenance (your standing duty)

Update the bank (`docs/`) at the end of every working session, whenever the human reports a
milestone, ruling, or state change, and whenever you notice the bank has drifted from
reality.

## 6. The no-tests law and the feel checklist

There are no automated gameplay tests. There will never be tests. CI enforces only the
credits (`tools/attr_lint.py`) — nothing about gameplay. The feel checklist
(`docs/ROADMAP.md` §4) is the entire regression suite; it is run by hand at every milestone
gate, and a failed checkbox blocks the tag. Do not build test infrastructure. Do not
"improve" this.

## 7. Workflow notes (learned the hard way, inherited from witchgame)

- **New or moved global classes need a Godot rescan before headless runs.** The class
  cache maps `class_name` to path and is regenerated by an editor scan. After adding a
  script with a new `class_name` or moving any scripts: reload the project in the open
  editor (Project → Reload Current Project), or headless:

      Godot --headless --editor --quit --path godot

  Otherwise the next headless run lies.

- **GDScript house style, by hand.** Tabs, 4-wide. Three-line `##` file header at the top
  of every `.gd` file; one `##` docstring line directly above every func (same indent);
  single `#` one-liners only inside function bodies; `# -- Section ------` banners at
  class scope. There is no linter here and there will never be one — the discipline is
  the point.
- **Docstrings are the documentation.** Write them dense: what the func does, inputs,
  return value, invariants the caller must know. Future sessions read them cold.
